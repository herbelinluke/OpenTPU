# Understanding Your Verilator Build

## What Verilator Did

When you ran Verilator on `tpu.v`, it:

1. **Parsed** your Verilog design
2. **Compiled** it into C++ classes
3. **Generated** simulation code in `obj_dir/`

## Key Files in `obj_dir/`

### Core Model Files
- **`Vtpu.h`** - C++ header with the model interface
  - Defines the `Vtpu` class with all I/O ports
  - Ports: `clk`, `rst`, `hostmem_*`, `weights_dram_*`, `halt`, etc.
  
- **`Vtpu.cpp`** - Model implementation (design-independent parts)

- **`Vtpu__ALL.a`** - Static library containing the compiled model
  - This is what you link against in your test harness

- **`Vtpu`** - Executable (if built with `--exe`)
  - Currently uses `Vtpu__main.cpp` which is very basic
  - Just runs simulation until `$finish` (which never happens)

### Generated Implementation Files
- **`Vtpu___024root*.cpp`** - Internal implementation files
  - Verilator splits large designs into multiple files
  - The `024root` refers to the root module
  - `DepSet_*` files handle dependency sets for optimization
  - `__Slow` variants are for slower evaluation paths

- **`Vtpu__Syms.*`** - Symbol table for debugging/inspection

- **`Vtpu.mk`** - Makefile for building the model
  - Generated by Verilator
  - Includes all dependencies

### Support Files
- **`verilated.*`** - Verilator runtime library
- **`*.d`** - Dependency files (for Make)
- **`*.o`** - Object files

## The Problem with `Vtpu__main.cpp`

The generated `Vtpu__main.cpp` is a minimal template that:
- Creates the model
- Toggles clock
- Calls `eval()`
- **But doesn't:**
  - Drive any inputs (memory, weights)
  - Handle memory interfaces
  - Load programs
  - Check for halt
  - Generate useful output

## Solution: Custom Test Harness

The `test_tpu.cpp` file I created provides:

1. **Memory Models**
   - Host memory (simulated RAM)
   - Weights DRAM (simulated weight storage)

2. **Interface Handlers**
   - Responds to `hostmem_re` (read requests)
   - Responds to `hostmem_we` (write requests)
   - Handles `weights_dram_read` (weight requests)
   - Transfers weight data in chunks

3. **Clock and Reset**
   - Proper reset sequence
   - Clock toggling
   - Cycle counting

4. **Monitoring**
   - Halt detection
   - Assertion checking
   - Progress reporting
   - VCD trace generation

## How to Build and Run

### Step 1: Build the Test Harness

```bash
make -f Makefile.verilator
```

This compiles `test_tpu.cpp` and links it with `Vtpu__ALL.a`.

### Step 2: Convert Memory Files

The Python simulators use numpy `.npy` files, but C++ needs binary:

```bash
python3 convert_mem.py simplemult_hostmem.npy simplemult_hostmem.bin --format hostmem
python3 convert_mem.py simplemult_weights.npy simplemult_weights.bin --format weights
```

### Step 3: Run Simulation

```bash
cd obj_dir
./test_tpu ../simplemult.out ../simplemult_hostmem.bin ../simplemult_weights.bin --trace ../trace.vcd
```

## Understanding the Interface

### Host Memory Interface
```
TPU → Test Harness:
  hostmem_re: "I want to read"
  raddr: "Read from this address"
  
Test Harness → TPU:
  hostmem_rdata: "Here's the data"

TPU → Test Harness:
  hostmem_we: "I want to write"
  hostmem_waddr: "Write to this address"
  hostmem_wdata: "Here's the data"
```

### Weights DRAM Interface
```
TPU → Test Harness:
  weights_dram_read: "I want weights"
  weights_dram_raddr: "From this address"

Test Harness → TPU:
  weights_dram_valid: "Data is ready"
  weights_dram_in: "Here's the weight chunk (512 bits)"
```

Weights are transferred in chunks because:
- Each tile is 64 bytes (8x8 for MATSIZE=8)
- DRAM interface is 512 bits (64 bytes) wide
- But we need to send it in 8 chunks of 64 bits each
- The test harness handles this chunking automatically

## Debugging Tips

### View Waveforms
```bash
gtkwave trace.vcd
```

Look for:
- `clk` - Clock signal
- `rst` - Reset signal
- `halt` - When simulation should stop
- `hostmem_re`, `hostmem_we` - Memory activity
- `weights_dram_read` - Weight requests

### Common Issues

1. **Simulation hangs**
   - Check if program has HLT instruction
   - Increase `--max-cycles` limit
   - Check if memory addresses are valid

2. **Memory errors**
   - Verify memory files converted correctly
   - Check address ranges match expectations
   - Ensure MATSIZE matches between config.py and test harness

3. **Assertion failures**
   - Check `assertion0` and `assertion1` signals
   - Look at waveform around failure time
   - Compare with Python simulator behavior
